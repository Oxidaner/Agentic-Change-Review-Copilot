# Local Development

## Current Reality

The repository serves the review-centric API surface.

Default endpoints:
- `POST /api/v1/reviews`
- `GET /api/v1/reviews/{review_id}`
- `GET /api/v1/reviews/{review_id}/timeline`
- `POST /api/v1/reviews/{review_id}/decision`
- `POST /api/v1/reviews/{review_id}/retry`
- `GET /api/v1/reviews/{review_id}/report`
- `POST /api/v1/reviews/{review_id}/evaluation`
- `GET /api/v1/review-metrics`
- `POST /api/v1/webhooks/github/pull-request`

The active product surface lives under `internal/review`.

## Start With Docker Compose

```bash
docker compose up --build
```

The API will be available at `http://localhost:8080`.

## Key Environment Variables

- `PORT`: HTTP listen port, defaults to `8080`
- `DATABASE_URL`: when set, the API uses PostgreSQL instead of the in-memory store
- `AUTO_MIGRATE=1`: runs the SQL files under `migrations/` on startup
- `GITHUB_WEBHOOK_SECRET`: when set, the GitHub PR webhook endpoint requires a valid `X-Hub-Signature-256` HMAC signature

## Analyzer Configuration

The API composition root opts into config-based analyzer selection explicitly by constructing the review service with `review.WithAnalyzerFromConfig()`.

Config file layout:
- `config/review-agent.json`: tracked base config for the analyzer runtime
- `config/review-agent.local.json`: optional local-only override for secrets and machine-specific values

Runtime behavior:
- if config is present, valid, and enabled, the API loads the configured analyzer
- if config is absent, invalid, or disabled, startup continues with the heuristic analyzer
- if the configured analyzer fails during a review run and the heuristic analyzer succeeds, the pipeline records `mode=agent_runtime_with_fallback` and `analyzer=agent_runtime_fallback`

## GitHub Webhook Adapter

A narrow GitHub PR webhook adapter is available at `POST /api/v1/webhooks/github/pull-request`.

Supported actions:
- `opened`
- `reopened`
- `synchronize`
- `ready_for_review`

Unsupported PR actions are accepted but intentionally ignored, which keeps upstream webhook delivery simple while avoiding unnecessary review creation.

If `GITHUB_WEBHOOK_SECRET` is configured, webhook requests must also include a valid `X-Hub-Signature-256` header generated by GitHub for the raw request body.

Minimal example:

```json
{
  "action": "synchronize",
  "number": 42,
  "repository": {
    "name": "gateway-service",
    "full_name": "octo/gateway-service"
  },
  "pull_request": {
    "number": 42,
    "title": "adjust auth routing",
    "head": {
      "ref": "feature/auth-routing",
      "sha": "def456"
    },
    "base": {
      "ref": "main",
      "sha": "abc123"
    }
  }
}
```
